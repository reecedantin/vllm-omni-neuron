## Introduction

[π0.5](https://www.physicalintelligence.company/download/pi05.pdf) is a Vision-Language-Action
(VLA) policy from Physical Intelligence: a PaliGemma (SigLIP vision + Gemma-2B language model)
prefix conditions a Gemma-300M action expert with AdaRMS timestep modulation, which predicts a
continuous action chunk via flow matching. π0.52 is the same action path with an added
hierarchical-language step: it first generates a short low-level subtask from the high-level
instruction (greedy decode through PaliGemma's own LM head), then conditions the action expert
on that subtask instead of the raw instruction.

Checkpoints are [LeRobot](https://github.com/huggingface/lerobot) exports
(`lerobot/pi05_base`, `lerobot/pi052_base`); this port vendors the upstream vLLM-Omni pi0.5
modeling code (not present in the installed vllm-omni 0.24 release) rather than carrying a
standalone implementation, per the onboarding guide's "subclass over standalone" rule --
`vllm_omni_neuron/diffusion/models/pi0/_vendor/pi05/`, byte-identical to upstream apart from
import paths and edits marked `# neuron:`.

π0.5/π0.52 is supported for inference serving with vLLM Omni using the Neuron SDK on AWS
Trainium2 (`trn2`).

The checkpoints derive from PaliGemma and are distributed under the
[Gemma license](https://ai.google.dev/gemma/terms); the PaliGemma tokenizer repo
(`google/paligemma-3b-pt-224`) is gated on Hugging Face.

**Compatible model checkpoints:**

| Model | Hardware | Quantization |
|-------|----------|---------------|
| lerobot/pi05_base | Trn2 | BF16 |
| lerobot/pi052_base | Trn2 | BF16 |

### Recommended configuration

The `pi052_base` checkpoint stores 4.14B parameters: SigLIP + projector 0.41B, the Gemma-2B LM
1.98B, its token embedding 0.53B (stored twice: `embed_tokens` and the tied PaliGemma `lm_head`),
the 300M action expert 0.43B and the action expert's `lm_head` 0.26B, which inference never
reads. Loaded, that is 3.62B unique parameters. HBM on one core (bf16): 5.94 GB of tensors for the
action path; 7.99 GB with pi0.52's subtask graphs (the decode step's packed QKV/O copy and the KV
cache), plus ~2.3 GB of graph scratchpad. Either fits one NeuronCore's ~24 GB (LNC=2), so TP=1 on
a single core is the recommended and default layout:
[`examples/pi0/pi052_stage.yaml`](../../examples/pi0/pi052_stage.yaml). Served there, a pi0.52
request on a real LIBERO observation with a 12-token subtask takes **269 ms** warm (first request on
an empty compile cache 241 s, on a warm cache 31 s; see Performance).

TP=2 over the PaliGemma LM (query heads, MLP columns and the vocabulary split over two cores of
one chip; vision tower and action expert replicated) is the option when two cores are available
and latency matters: the same request takes 213 ms (each subtask token costs 9.2 ms instead of
12.8 ms): [`examples/pi0/pi052_stage_tp2.yaml`](../../examples/pi0/pi052_stage_tp2.yaml).

## Quantization

BF16 only. The model fits one NeuronCore in BF16 (5.94-7.99 GB HBM), so weight quantization buys no
fit and is not implemented. The vision tower dtype can be overridden with `PI05_VISION_DTYPE`
(`bf16` / `fp32`) for accuracy experiments.

## Architecture notes (what differs from the stock DiT pipelines this guide otherwise assumes)

- **No VAE, no scheduler, no text encoder in the Wan2.2 sense.** The "DiT" is the Gemma-300M
  action expert; the "text encoder" is PaliGemma's own Gemma-2B LM, shared with the action path
  (not a separate frozen encoder) -- the prefix's K/V cache is what the action expert
  cross-attends.
- **Two fixed-shape graphs** (`vllm_omni_neuron/diffusion/models/pi0/graphs.py`):
  `Pi05PrefixGraph` (images + language -> per-layer K/V, bidirectional) and
  `Pi05DenoiseGraph` (one Euler flow-matching step over the cached K/V). The 10-step schedule
  replays `Pi05DenoiseGraph` on the host, like Wan2.2 replays its DiT graph per scheduler step.
- **pi0.52 adds the subtask graphs**: `Pi05EmbedImagesGraph` (SigLIP once per request),
  `Pi05SubtaskPrefillGraph` (one bidirectional LM pass over the image + prompt prefix: the first
  token's logits plus every layer's K/V, compacted to the real tokens, as a `StaticKVCache`) and
  `Pi05SubtaskDecodeGraph` (one generated token through every LM layer with the shared
  decode-attention layer's `decode_step`; position-static, so one compiled graph serves every
  token). Generated tokens attend causally and the prompt never sees them, as in LeRobot's
  `select_message`. With `subtask_kv_cache: false` in `model_config` the decode falls back to
  `Pi05TextPrefixGraphCached` (the whole sequence re-run per token, same mask).
- **No custom NKI kernel** for the subtask decode: `decode_step` runs its verified torch path
  (its fused NKI kernel is opt-in via `VLLM_OMNI_NEURON_DECODE_STEP_NKI=1`).

## Accuracy Evaluation

Three tiers per the [onboarding guide](../model-dev/onboarding-models.md), cheapest first.

**Tier 1 (component, three-way):** `test/neuron/test_pi05_components_accuracy.py` --
`Pi05PrefixGraph` and `Pi05DenoiseGraph` against the vendored upstream CPU model via
`vllm_neuron.accuracy.testing.assert_close_three_way` (FP32 CPU baseline / BF16 CPU expected /
BF16 Neuron actual), on the shrunk M-tiny checkpoint.

**Tier 2 (single-step / full-model parity):** `test/unit/test_pi0_tiny.py` proves the CPU legs
(fp32 graphs vs. upstream fp32, bf16 vs. fp32) without a device; `examples/pi0/device_check.py`
runs the device leg on real `lerobot/pi052_base` weights:

| Comparison | rel-L2 | cos | MSE |
|---|---|---|---|
| Device bf16 vs. CPU fp32 upstream (job 1005-163628) | 0.74% | 0.99997 | 1.0e-5 |
| CPU bf16 graphs vs. CPU fp32 (dtype error alone) | 2.29% | -- | -- |
| Device bf16 vs. LeRobot's own fp32 kernel (`examples/pi0/lerobot_parity.py`, 2026-10-03) | 0.72% | 0.999975 | 9.7e-6 |
| Our CPU fp32 graphs vs. LeRobot fp32 | 8.5e-7 | 0.9999999 | 1.4e-13 |

**Tier 3 (end-to-end, golden):** `examples/pi0/lerobot_e2e_parity.py` +
`examples/pi0/e2e_parity_ours.py` -- the full pipeline (pi0.52 subtask generation -> low-level
prompt -> action chunk) against LeRobot's own `predict_action_chunk` on one fixed observation,
with the flow-matching noise pinned so the comparison is deterministic: **MSE 9.2e-14, cos
0.9999999, rel-L2 6.9e-7** -- machine precision.

**Served (device, real inputs):** `examples/pi0/run.py` served the request, and
`examples/pi0/served_parity.py` replays the saved observation and noise through the CPU fp32
pipeline (and CPU bf16 for the bar). It also reads every rank's `PI0_STATS_FILE` record
(digests of the action chunk and the subtask token ids) to check that all ranks agree. Inputs are
LIBERO frames from a demo episode: the agent-view camera as `base_0_rgb`, the wrist camera as
`left_wrist_0_rgb`, `right_wrist_0_rgb` left out and masked (as LeRobot does for a missing camera),
the 8-d robot state zero-padded to the checkpoint's 32, and the episode's instruction. 10 flow
steps, fixed noise (jobs 1005-153328, 1005-163628 and 1005-170956; CPU 1005-163656 and 1005-170956):

| Observation | Subtask | Bar | TP=1 | TP=2 | TP=2 ranks agree |
|---|---|---|---|---|---|
| LIBERO ep. 0, frame 100 | natural (EOS at once, task text kept) | 1.06% | 0.22% | 0.28% | yes, 11/11 requests |
| LIBERO ep. 2, frame 150 | natural (empty, task text kept) | 1.00% | 0.24% | 0.22% | yes, 6/6 |
| LIBERO ep. 0, frame 100 | fixed 12 tokens (`min_new_subtask_tokens`) | 4.30% | 2.44% | 2.51% | yes, 11/11 |
| Random frames, default task | natural (EOS at once) | 2.13% | **2.15%** | **2.34%** | yes, 11/11 |

In the natural rows the device subtask text equals CPU fp32. With 12 tokens forced, the base
checkpoint, which wanted to stop, writes byte tokens: device and CPU fp32 pick different ones, so the
action prompts differ. That row shows the error band, not token-exact parity. TP=1 and TP=2 produce
the same token ids there. Random-noise frames, the smoke-test input `run.py` uses for a camera
without `--image`, miss the bar by 0.02 (TP=1) and 0.21 (TP=2) points in this one draw. On the
action path alone (Tier 2, job 1005-163628) the device error is 0.74% against a 5.1% bar.

**Random-frame sweep** (`examples/pi0/served_sweep.py`, job 1005-175512, CPU 1005-175517): 12 draws
through one served engine per layout. Eight noise seeds share frame seed 0, and four more frame
seeds share noise seed 0. Every draw has its own CPU fp32 reference and its own bar:

| Layout | Mean device error | Mean bar | Mean error / bar (max) | Mean error / CPU bf16 (median) | Misses | Ranks agree |
|---|---|---|---|---|---|---|
| TP=1 | 1.62% | 2.85% | 0.57 (1.06) | 1.45 (1.61) | 2 / 12 | -- |
| TP=2 | 2.00% | 2.85% | 0.70 (1.11) | 1.77 (1.87) | 4 / 12 | yes, 12 / 12 |

Every miss is on frame seed 0, by at most 11% of the bar: 2 of its 8 noise draws at TP=1 and 4 at
TP=2. On that frame the device error is 1.2-2.6x CPU bf16 at TP=1 and 1.7-2.9x at TP=2. The other
four frames pass with wide margin (error 0.1-0.4 of the bar; on three of them the device error is
below CPU bf16's own). The excess is specific to that input, not systematic. On it, TP=2 adds about
0.5 points over TP=1 (mean 2.70% vs. 2.19%). Both ranks returned identical action chunks and
subtask ids for every draw.

**Bar used throughout** (device checks, served parity, TP): action rel-L2 vs. CPU fp32 ≤ k × (CPU
bf16 rel-L2 on the same input) + 0.5%, with **k = 2**. `device_check.py`, `device_check_base.py` and
`served_parity.py` compute it per run (`--bar-k`). The LeRobot comparisons of our CPU fp32 path
(Tier 2's last row, Tier 3) are fp32 vs. fp32 implementation checks with the gate action MSE ≤
1e-3 and cos ≥ 0.999. Both pass at machine precision.

## Performance

**Headline: served pi0.52 on a real observation.** Warm median of 10 requests through
[`examples/pi0/run.py`](../../examples/pi0/run.py) `--profile --repeat 10`, bf16, 10 flow steps. The
input is LIBERO episode 0, frame 100 with its instruction (two real 224 px cameras plus one masked,
real state; see Accuracy), with a 12-token subtask. LeRobot's subtask examples (e.g. "put the white
mug on the left plate", 8 tokens) fit that length. The `pi052_base` checkpoint itself stops its
subtask at once on these frames, so the length is fixed with `min_new_subtask_tokens` =
`max_new_subtask_tokens` = 12. Each decode step costs the same whatever the token. Measured on a
quiet host (1-minute load average 13-17 before every timed request) after one uncounted warm-up
request, job 1006-134101 (warm cache); empty-cache first request from job 1005-153328:

| Layout | Served request | Subtask stage (12 tokens) | Action prefix + flow loop | First request, warm cache | First request, empty cache |
|---|---|---|---|---|---|
| **TP=1, 1 core (recommended)** | **269.4 ms** | 192.7 ms | 68.8 ms | 30.6 s | 241.0 s |
| TP=2, 2 cores | **213.3 ms** | 146.1 ms | 61.0 ms | 30.4 s | 200.7 s |

The first request on an empty cache includes compiling every graph and the host weight load
(~40 s of it). Host stages (decode, preprocess, prompt, postprocess) total ~2 ms, and the
client -> worker transport ~2 ms.

Requests scale with the subtask length: on one core, about 130 ms with a 1-token subtask plus
12.8 ms for each further token; at TP=2, about 117 ms plus 9.2 ms. With a 1-token subtask, where
the model stops at once, the served request is 129.7 ms on 1 core and 117.4 ms at TP=2 on the same
LIBERO frame, and 128.0 / 116.9 ms on random frames (jobs 1006-134101, 1006-140651). One LIBERO
frame (episode 0, frame 0) leads the base checkpoint to a 42-token byte-token subtask, and that
request takes 652 ms (TP=2: 37 tokens, 459 ms), as the per-token cost predicts.

**Optimization levers** (2026-10-04, before this round's rebase): one core, three random 224 px
cameras, 1-token subtask. Measured by
[`examples/pi0/latency_levers.py`](../../examples/pi0/latency_levers.py), which toggles each lever
on the same loaded pipeline with stages synced:

| Stage | Before | After | Change |
|---|---|---|---|
| SigLIP + projector | 14.1 ms, run twice (subtask, action prefix) | 14.1 ms, run once | one pass reused by the action prefix |
| Action prefix (LM over images + prompt) | 50.2 ms (incl. SigLIP) | 37.0 ms | `Pi05PrefixFromEmbeddingsGraph` |
| Flow-matching loop, 10 steps | 58.7 ms (host Euler update) | 31.3 ms | per-step device graph + AdaRMS tables |
| Subtask decode, per generated token | 14.8 ms (logits to host, host argmax) | 14.0 ms | argmax + suppression in the graph |
| `pipeline.forward()` (1-token subtask + action chunk) | 164.5 ms | 122.1 ms | -26% |
| Served request, 1 core | 170.9 ms | 127.9 ms | -25% |
| Served request, TP=2 (2 cores) | -- | 112.2 ms | -34% vs 1-core before |

- **Flow loop.** Each step used to copy `v_t` to the host and `x_t` back. Now one graph per Euler
  step updates `x_t` on the device (`denoise_mode: device`), and the AdaRMS `dense(cond)` of all 37
  norms is computed once per schedule on the host and fed in as a `[n, 37, 3W]` table
  (`adarms_tables: true`), as upstream's math but outside the step. Same 10 steps without tables:
  host 58.7 / device 52.5 ms; with tables host 37.4 / device 31.3 ms. Unrolling all 10 steps into
  one graph (`denoise_mode: unrolled`) compiles in ~500 s and is slower (49.9 ms without tables,
  80.6 ms with them), so it is not the default.
- **Subtask greedy.** The decode graph alone costs 11.6 ms/step (HBM-bound: the 2.5B LM plus
  `lm_head` per token); the in-graph argmax over the 257k vocabulary adds ~1.1 ms of device time
  and removes ~1.9 ms of host sync and 1 MB logits copy, net -0.8 ms/token. Reading token ids back
  only every 4 steps (`subtask_sync_every: 4`) reaches 12.2 ms/token for long decodes but launches
  up to 3 wasted steps after an early EOS, so the default checks every step.
- **TP=2** (two cores of one chip, served): see the headline table. The per-token subtask cost
  goes from 12.8 to 9.2 ms and the action stage from 68.8 to 61.0 ms. Both ranks return identical
  action chunks and subtask ids (Accuracy).
- **Measured and not adopted as a speed lever:** cameras as raw bytes (`{"data", "shape",
  "dtype"}`, still accepted) transport in ~1.5 ms either way at 224 px. With 8 host threads for
  preprocessing, the realistic request took 278.0 / 273.5 ms, against 276.4 / 276.4 ms with the
  default (job 1005-163628, interleaved runs). Preprocessing is ~1.3 ms either way, and the run
  spread is in the device subtask stage, which the threads do not touch. `host_threads` (and
  `PI0_HOST_THREADS`) therefore defaults to 0, which keeps the worker's thread setting.

pi0.52 subtask decode, KV-cached (default) vs. re-prefill (`subtask_kv_cache: false`), same build,
measured by [`examples/pi0/subtask_kv_check.py`](../../examples/pi0/subtask_kv_check.py):

| Warm, bf16, single core | Re-prefill | KV-cached | Speedup |
|---|---|---|---|
| Subtask stage, 1 generated token (EOS) | 89.8 ms | 55.4 ms | 1.6x |
| Subtask stage, 16 generated tokens | 1226 ms | 239 ms | 5.1x |
| Per additional generated token | 75.7 ms | 12.3 ms | 6.2x |
| Full `pipeline.forward()` (subtask + 10-step action chunk) | 208.9 ms | 174.6 ms | 1.20x |
| Served request, warm median (`examples/pi0/run.py --profile`) | 211 ms | 175 ms | 1.21x |

The KV-cached path runs the image + prompt prefix once (`Pi05SubtaskPrefillGraph`) and then one
`decode_step` graph per token; the re-prefill path re-runs the whole LM (and an `lm_head` over every
position) per token. Accuracy, teacher-forced over 16 tokens x 3 prompts against CPU fp32 logits:
device KV-cached rel-L2 0.61% mean / 2.6% max, device re-prefill 0.69% / 3.2%, pure CPU bf16
0.90% / 3.9% -- the KV-cached decode is inside the bf16 band. Greedy tokens: CPU fp32 KV-cached ==
re-prefill == LeRobot `select_message` (both `use_kv_cache` settings), token for token, including
fixed-length decodes; on device 8 of 9 decodes match exactly, the ninth (dummy images, a
near-tie among byte tokens) flips at token 3, as pure CPU bf16 also does on that prompt.

**Image-prefix caching** (`Pi05EmbedImagesGraph` + `Pi05TextPrefixGraphCached`, on by default)
runs the vision tower once per request instead of once per generated subtask token --
`enable_subtask_generation(..., cache_image_prefix=True)`. CPU parity: the cached decode
produces byte-identical greedy token ids to the uncached path.

## Known limitations

- **`pi052_base` does not write useful subtasks.** On the LIBERO frames tested, its greedy subtask
  is empty (EOS first; LeRobot then keeps the instruction as the subtask) or a run of byte tokens
  (42 tokens on episode 0, frame 0). Where it stops at once, the device text equals CPU fp32. In the
  byte-token run, the device, CPU fp32 and CPU bf16 pick different tokens (near-ties). A checkpoint
  fine-tuned for hierarchical subtasks is needed for meaningful ones. The headline therefore fixes
  the subtask at 12 tokens (`min_new_subtask_tokens`, a benchmarking knob; default 0).
- **One random-noise camera frame sits at the accuracy bar.** Over a 12-draw sweep the mean device
  error is 0.57x the bar at TP=1 and 0.70x at TP=2. All misses (2 / 12 at TP=1, 4 / 12 at TP=2, at
  most 1.11x the bar) are on the same random frame (seed 0) with different noise draws (Accuracy).
  Real LIBERO frames pass at both layouts; with the natural subtask the error is about a quarter
  of the bar.
- **Subtask length is bounded** by the largest prompt bucket and the KV cache:
  `Pi052SubtaskGenerator.buckets` (default up to 256 tokens) and a cache of
  `ncam x 256 + 256` slots (1024 for three cameras); a longer request raises.
- **The subtask decode reads one token id back per step** to stop at EOS. The step is
  HBM-bound (~11.6 ms of the ~14 ms); TP=2 is the remaining lever for long subtasks.
- **No NKI kernel path** for the action attention or the subtask prefill -- both run the
  SDPA-equivalent torch path from `graphs.py` under `torch.compile`. The subtask decode step uses
  the shared `decode_step` torch path; its fused NKI kernel is opt-in
  (`VLLM_OMNI_NEURON_DECODE_STEP_NKI=1`) and not measured here.
- **Relative actions are implemented in the processor but untested on device** (the
  `pi052-base` / `pi05_base` checkpoints used for parity ship `use_relative_actions=False`).
- **Batch size 1.** Like Wan2.2, concurrent requests are not yet batched into one forward pass.
